版本：2.0.0  
制定日期：2026-09-28  
制定者：人类队长  
授权来源：2026-09-28 队长晚间消息

## 协议目的

本协议定义 FC-E 异构交叉评审的条目规范和机械校验标准，确保评审过程的客观性和可验证性。

## 条目类型规范

### 1. Hypothesis（假设类）

用于表述待验证的观点或推测，明确标注不确定性。

**格式要求：**
- 类型标识：`hypothesis`
- 内容：待验证的命题
- 状态：`待验证`
- 证据：待收集

**示例：**
```yaml
type: hypothesis
content: "代码中存在潜在竞态条件，可能导致熔断器状态不一致"
status: "待验证"
evidence: []
```

### 2. Fact（事实类）

用于记录可验证的客观事实，必须包含精确的技术证据。

**格式要求：**
- 类型标识：`fact`
- Commit：确切提交哈希
- File：文件路径及行号
- Quote：逐字引用的代码内容
- Verification：机械校验结果

**示例：**
```yaml
type: fact
commit: "73e64cc70116ac658d85591d082c0684a4952c99"
file: "swarm/breaker.py:192"
quote: "# TODO-HUMAN-REVIEW"
verification: "PASS"
```

## 机械校验标准

### 事实类条目的验证规则

1. **Commit 验证**：提供的提交哈希必须在仓库中存在
2. **文件路径验证**：文件必须存在且可访问
3. **行号验证**：指定行号必须存在
4. **内容匹配验证**：引用内容必须与源文件完全匹配
5. **逐字匹配**：使用精确字符串匹配算法验证引用内容

### 验证结果状态

- `PASS`：所有验证条件满足
- `FAIL`：验证失败
- `INVALID`：引用不匹配，自动标记为无效
- `NOT_FOUND`：找不到指定的提交/文件/行
- `NOT_RUN`：待机械校验或未执行

## 引用验证机制

对于 `fact` 类型的条目，必须执行以下机械验证步骤：

1. 验证 Commit 哈希的存在性
2. 检查文件路径的有效性
3. 确认行号的准确性
4. 执行逐字匹配验证
5. 记录验证结果

**重要说明：** 匹配仅证明引用存在，不证明推论成立。

## 评审流程

1. **条目生成**：评审者按上述格式生成条目
2. **机械验证**：自动验证 `fact` 类型条目的准确性
3. **状态标记**：为每个条目标记验证状态
4. **结果汇总**：生成包含验证结果的评审报告

## 质量保证

- 所有 `fact` 条目必须通过机械验证，否则标记为 `INVALID`
- `hypothesis` 条目不需要机械验证，但仍需明确标注待验证状态
- 不允许在 `fact` 条目中包含主观推论而不进行验证
- 验证失败的 `fact` 条目不得用于支持结论

## 版本管理

- v2.0.0（2026-09-28）：初始正式版本，取代之前的非正式评审方式
- 新增 `verification` 字段用于机械校验结果
- 强制要求 `fact` 类型条目的精确验证
- 明确标注验证结果不影响推论有效性

## 注意事项

1. 本协议旨在提高评审的客观性，而非限制评审内容
2. 机械校验仅验证引用的准确性，不评估推论的正确性
3. 评审者仍需对推论和结论承担责任
4. 验证失败的条目应重新检查或移除
