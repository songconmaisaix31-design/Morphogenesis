## 1. 产品定位与已确认需求

### 1.1 要解决的问题

单次 Agent 会话难以持续承担文献调查、交叉质疑、跨领域联系、代码实现与实验迭代。用户目前需要不断重新说明上下文、手动比较结论并协调交接。Morphogenesis 的产品目标是降低这种组织负担，让协作产生可追溯的新问题、方法和可运行成果，而不是简单叠加更多聊天窗口。[U02]

**Swarm Harness** 指位于单个 Agent Harness 之上的研究环境：保留成员原生推理、工具和会话能力，提供共同研究对象、局部工作发现、可追溯协作、受控执行和成果继承。它不替换各品牌 Agent，不要求全部成员使用同一模型或编程框架。

### 1.2 已确认的十项产品决策

| 编号 | 决策 | 对 R1 的约束 |
|---|---|---|
| D01 | 局部互动与自组织是核心 | 不能把所有研究预先编成固定角色流水线 |
| D02 | 首批方向是 Swarm／去中心化协作和数学物理模型计算实现 | 支持这些计算研究切片，不承诺覆盖所有专业领域 |
| D03 | 新候选代码必须进入首版 | 文献、讨论和假设能够产生新代码，不限于注册示例 |
| D04 | 一个本地研究环境结合云端资源 | 本地主机是工作区与状态宿主；云推理与指定云计算是独立后端 |
| D05 | 首版不做跨电脑 Swarm／多人实时共用 | 专家可在自己电脑独立运行，不形成分布式共享账本 |
| D06 | 专家提供选题、条件、评审与实验支持 | 首版由负责人输入／导入意见；意见不是自动成立的科学事实 |
| D07 | 在目标和资源授权内自主推进 | 常规调查、提议、编码和已获准类别的验证不逐步请示 |
| D08 | 奖励依据证据与研究贡献 | 可靠反例也是正贡献；意见数、任务数、token 数不算贡献 |
| D09 | 好路线增加后续机会，低价值路线渐减投入 | 减少未来投入，不删除历史；允许有根据地重开 |
| D10 | 阶段成果有价值，论文是长期产物 | 支持调查、推导、代码、实验与失败结论积累；不承诺一键论文或必然涌现 |

D01—D10 源自本次需求对齐。[U02] 以下具体接口、默认规模和技术选择是本稿的设计建议，应通过实现评审确定，不冒充用户逐项指定。

### 1.3 首版用户与成功定义

首要使用者为项目负责人或单个研究者。学科专家通过负责人补充意见、资料或独立实验结果；无须共享在线账户和协同编辑。

一次有价值的使用应当使研究者看见：问题如何从资料中形成、哪些成员提出了不同解释、哪个证据改变了方向、实验实际算出了什么，以及后续工作如何使用前一阶段成果。研究可以得出负结论；不能为了“成功”删除不利结果。

产品功能通过不等于证明协作优于单体。**涌现是研究目标；可追溯的知识组合、非预置分支和证据驱动行动，是首版必须展示的机制行为。**

## 3. 首版范围与关键用户旅程

### 3.1 包含与不包含

| R1 必须包含 | R1 不要求 |
|---|---|
| 自然语言研究目标、论文／代码／数据和专家意见输入 | 在线多人账号、跨主机一致性、共同编辑 |
| 有来源的假设、质疑、实验提议和研究分支 | 无限扩员、无限背景运行 |
| 不同原生成员自主发现和认领合法任务 | 强行兼容所有 Agent 或统一所有原生会话格式 |
| 根据资料生成新 Python 候选实验代码 | 首版执行全部语言、任意系统命令、自动系统安装 |
| 隔离运行、独立验证、反例贡献、实际继承 | 自行修改宿主、核心执行器、预算规则或可信判据 |
| 基于证据调整后续工作机会 | 保证最优路由、保证产生新发现、无成本上限探索 |
| 本地计算与云模型协同；明确后端接口 | 分布式 Swarm、GPU 集群、跨电脑任务调度 |
| 阶段摘要、代码／结果／来源导出 | 一键发表、自动投稿或临床／核设施／航天设备控制 |

本地 CPU 是 R1 必备执行档。已授权且通过能力验证的本地 GPU 或指定云计算后端可启用；缺失时明确标不支持，不假装云模型推理已经提供实验算力。计算研究领域不限制专家学科，但本版仅执行安全、离线的计算实验，不连接真实实验仪器。

### 3.2 J01：从论文与讨论到候选实验

研究者给出一个问题、一到数篇论文，以及允许使用的计算环境。不同成员提取关键主张、假设条件和已有方法；成员发现矛盾或跨领域联系后，可提出多个受限研究分支。临时规划角色可以提出任务，不垄断任务分配。

成员从局部工作集中自主认领，生成候选实现和实验提议。候选检查与实验计划获准后，执行器在隔离环境运行。独立复核者根据原始输出、参考计算或预设性质检查结果。有效新证据改变下一批任务和路线偏好。用户可在过程中追加意见，无须分别向各成员重述。

### 3.3 J02：研究 Swarm 自身的协作机制

群体可以生成模拟协作策略、任务分配器或交互规则的实验程序，在独立实验空间比较其行为。实验对象是候选模型或模拟程序，**不是运行中的 Morphogenesis 控制平面**。任何潜在改进只能产出提案和可复核代码，不能自行替换当前策略、验证器或权限。

### 3.4 J03：专家意见改变局部研究

负责人导入专家意见，注明来源、时间、适用领域和对应假设。相关成员收到有界提醒，形成检查或修订工作；无关研究继续。反对意见保留为意见或争议，不按专家身份直接标科学失败。专家在自己电脑运行的结果可作为“外部提供证据”导入，不能直接标成本机执行、独立沙箱复现或已采用。

## 4. 功能需求清单

以下 FR 编号用于开发和测试追踪。全部为目标行为；当前实现状态以第 2 节为准。

### 4.1 研究输入与共同上下文

**FR-01｜创建研究空间。** 用户提交自然语言目标、期望产物、资料、数据边界和资源授权。系统可提出澄清问题，但不得要求用户先写完所有任务和候选代码。正常研究只在目标、权限或重大风险变化时再次请求决定。

**FR-02｜资料导入与引用定位。** 接受本地 PDF／Markdown／文本、公开论文链接和代码仓库快照。保存来源、获取时间、版本／commit、许可证信息及页码／段落／代码行定位。抽取失败、公式不可靠、仅有摘要、无法获取全文都必须可见。不得从标题推断全文结论。

**FR-03｜共同研究记忆。** 保存研究问题、假设、支持和反对证据、争议、已尝试路线、程序及实验记录。未验证观点可以共享，但与已验证结果分开。新成员能读取必要背景与未解决问题，不要求恢复其他品牌完整私有会话。

**FR-04｜局部上下文包。** 根据项目权限、研究分支、任务依赖、能力和引用关系选取上下文。包内包含摘要、原始来源链接、当前分歧、适用条件和下一步约束；摘要须能回到原文。默认不广播全量论文、日志或所有 Agent 对话。

**FR-05｜持续研究。** 长研究由多个有界运行片段组成，项目知识跨片段保存；预算到期、机器关闭、会话压缩均不删除项目。不通过重建 run ID 规避预算，也不强求一个 CLI 进程永久在线。

### 4.2 自组织工作与成员接入

**FR-06｜研究工作提议。** 成员可以提出新问题、子任务、替代路线、反例检查、跨领域联系与实验提议。提议必须绑定目标、依据和预期贡献。宿主检查授权、依赖、重复性与派生配额后，可在预批准范围内成为任务；并非每项提议都需负责人点击。

**FR-07｜自主认领。** 共享环境提供合法候选及推荐，成员可遵循或覆盖；认领时重新检查权限、依赖、scope、租约和执行预算。记录推荐、实际选择、原因摘要与当前 token。提示词、UI 排序或某个规划成员不得拥有绕过账本的写权。

**FR-08｜动态协作。** 同一个人或 Agent 可以在不同任务中承担调查、实现、批评或复核职责；角色不是永久身份。可以进行依赖接续和有限定向协作，但关键发现必须进入共同研究记录，不能只存在于私聊里。对同一结果的独立批准不能由其作者自我完成。

**FR-09｜原生成员。** 默认使用已安装原生工具与明确选择的账户／模型，由产品创建或恢复研究会话；只管理本产品拥有的进程树。保留原生能力不等于放开宿主 shell 或所有原生工具。外部已有实例仅在协议明确支持时连接，默认无权结束其服务或其他会话。

**FR-10｜成员替换。** 成员退出后，其他成员在确认任务状态及无未知执行效果后，可在新身份／token 下接续工作；知道哪些结果已经验证、哪些步骤不可重放。单一研究成员离线不阻止其他独立分支工作；本地主机停止仍会停止该宿主执行，不宣称无任何单点。

### 4.3 研究方向、专家意见与资源机会

**FR-11｜专家意见。** 支持负责人添加／导入有署名和条件的评审意见，关联到问题、分支或候选。保留不同意见和处理依据；专家意见影响关注程度或触发检查，不直接成为可执行权限或已验证科学结论。

**FR-12｜贡献与路线分离。** 分别记录执行可靠性、假设结论和贡献价值。有效反证降低被反驳路线的后续投入，同时认可找到反证的贡献。程序崩溃、超时、认证错误不作为科学反证。

**FR-13｜投入调整。** 在固定总授权内，依据有效证据、待解决不确定性、适用性和验证成本调整后续调查／实验机会。降低优先级、休眠和重开须有原因。不得把“专家更喜欢”“任务完成多”作为唯一奖励。

**FR-14｜探索与多样性。** 合法但暂时证据较少的路线有有界探索机会；明显不适用或越权路线无探索资格。同源论文重述、同一回执重读、复制同一实验不得重复计为独立贡献。不同模型品牌不能自动视为独立证据来源。

### 4.4 动态候选、验证与继承

**FR-15｜新候选程序。** 根据论文、讨论、假设或前序结果自主生成／修改 Python 实验代码，并产生独立候选版本。允许正常迭代，不要求与注册示例字节相同。禁止修改原始数据、可信验证器、审计、宿主配置或已批准候选的历史正文。

**FR-16｜实验提议与计划。** 每次实验绑定候选、数据、依赖环境、参数、随机种子、评价方法和资源请求。评价标准必须在正式评价输出出现前冻结；Agent 可提议标准，但不能自行获得可信判据写权。诊断测试与正式评价分开记录。

**FR-17｜检查后隔离执行。** 先完成范围、语法、依赖、潜在危险操作和资源检查，再在独立沙箱执行。静态检查不证明安全；没有已验证隔离能力时，可以继续非执行讨论，但不能偷偷退回宿主运行候选。

**FR-18｜可信判定与独立复核。** 执行器采集原始输出，可信评价器重新计算指标；独立成员审查论据及复现实验。输出是否有效、假设是否支持、贡献是否可接受分别裁决。未知或争议保留，不能多数投票制造 PASS。

**FR-19｜真实成果继承。** 后续不同任务／成员检索并判断源成果适用性，在自己的运行中再验证，然后实际使用代码或方法。代码应用复用原消费执行与采用回执；文本观点的引用另标“引用／受其影响”，不能伪装成代码采用。改变条件时重新论证，不继承原 PASS。

**FR-20｜结果输出。** 导出研究摘要、源码、环境与重现实验说明、原始结果定位、反证与局限、来源及贡献记录。支持后续论文组织，不自动投稿，不把测试夹具包装成科研发现。

### 4.5 产品交互与可观测性

**FR-21｜研究工作台。** 在现有研究空间中提供目标／资料、当前假设与路线、成员、下一步和需要人决定的事项；自然语言交互与结构化对象互相可追溯，不只显示会话列表。

**FR-22｜事件时间线。** 显示提议、选择、认领、候选版本、运行、复核、反证、休眠、恢复、应用和采用。区分 HTTP 接受、实际启动、任务释放、执行完成、科学结论与采用；页面刷新不重发动作。

**FR-23｜成果与继承视图。** 让用户找到源资料、原假设、已验证结果、适用条件、子成果和采用凭据。能看见“为何不再推荐”，而不是只看见成功资产。

**FR-24｜拓扑可解释。** 研究图的边表示支持、反驳、依赖、引用、复现、采用或接续；节点状态来自后端。黏菌视觉表现可艺术化，但不是状态源。提供列表／低动画模式，实时与回放明确分开。

## 5. 领域对象、状态与事实权威

### 5.1 建议对象映射

以下是拟议领域契约，不宣称仓库已经存在同名类或数据库表。实现优先复用现有项目元数据、资产存储及 ID，不创建第二套任务账本。

| 对象 | 关键内容 | 权威与复用方式 |
|---|---|---|
| ResearchProject | 目标、资料、允许的研究域、授权引用、里程碑 | 产品项目元数据；运行片段另有原 swarm/run ID |
| ResearchBranch／Hypothesis | 主张、条件、父／关联分支、支持与反对来源、状态 | 新研究语义记录；任务状态仍来自 TaskLedger |
| Evidence／ResearchNote | 原始来源定位、观察或意见、适用条件、作者、审查状态 | 复用资产／报告引用；非文件候选不得硬塞成虚假代码补丁 |
| WorkProposal | 目标、branch、依据、所需能力、依赖、预期观察和粗略资源 | 经宿主验证后形成原账本任务，记录原 proposal 与 task 的关联 |
| CandidateProgram | 实际文件变更、来源、父候选、环境要求、生成会话 | 尽量复用 Candidate；动态验证采用新契约版本 |
| DynamicExperimentPlan | 候选与数据版本、环境、参数、检查、评估器版本、资源 | 扩展实验计划的版本化分支，不冒充旧 CaseId |
| Evaluation／Review | 执行有效性、假设判断、独立性、条件、理由、原始结果 | 新结果语义与现有实验报告关联；宿主／可信评价器写入结果 |
| Contribution | 被接受的研究贡献、来源和目标、接受依据、撤回／修订 | 引用现有结果／评审 ID 去重，不造另一套“完成证明” |
| ResourceOpportunity | 分支后续任务／实验机会、原因、策略版本 | 可重建派生偏好；实际预留仍由原预算账本完成 |

研究语义表可放入现有项目数据库的独立命名空间；代码位置以私库核对结果确定。它们描述科学关系，不复制执行状态、费用结算或 fencing。初版可使用 SQLite＋现有索引，不要求新增图数据库。

### 5.2 三轴结果模型

| 轴 | 建议状态 | 解释 |
|---|---|---|
| execution | not_run／running／succeeded／failed／cancelled／unknown | 计算是否执行及其外部效果是否确定 |
| hypothesis | not_evaluated／supported／refuted／inconclusive／disputed | 在声明条件与评价方法下，对假设的判断 |
| contribution | proposed／accepted／rejected／superseded | 这项研究贡献是否被独立依据接受 |

例：执行成功并产生可信反例，可以是 `succeeded / refuted / accepted`。执行超时但没有可信输出，应是 `failed / not_evaluated / proposed` 或被拒绝，不能写 `refuted`。

这组状态属于拟议新语义。旧 `scientific_verdict=passed/failed/not_evaluated` 继续可读，不直接改变其含义；迁移展示必须说明旧字段判断的对象。资产获准执行、方法获验证、补丁获应用、成果被采用也是不同阶段。

### 5.3 分支状态与版本

研究分支建议使用 `proposed → exploring → testing`，并可转为 `supported / disputed / dormant / refuted / archived`。这些不替代任务状态。`refuted` 必须注明条件；条件变化时形成新版本或新分支，不擦除旧反证。

任何候选、计划和评价标准变更都创建新版本与引用关系；已执行计划不可就地修改。贡献撤回通过追加更正事件影响未来派生偏好，原实验、费用和采用历史仍保留。

### 5.4 关联与幂等

复用现有 project、task、AgentId、AttemptId、session、fencing token、run、asset、report、ConsumptionExecution 和 AdoptionReceipt。研究事件必须能回到至少一个原始来源。

同一结果与同类贡献只接受一次；两个候选引用同一个结果不能双倍奖励。同一 UI／工具写请求可重复返回原结果，但不能重复启动原生会话、实验或应用。跨数据库写入中断必须保留未完成状态，并用现有结果事实恢复；恢复偏好不重跑科研。

## 6. 自组织协作与共同记忆机制

### 6.1 单个成员的有界局部循环

`读取局部上下文 → 发现／提出工作 → 查看合法候选 → 自主认领 → 调查／编码／提议实验 → 提交证据 → 复核或接续 → 更新共同记录 → 在剩余授权内继续。`

系统不要求成员遍历全项目，也不通过每轮全员广播完成协作。局部性由权限、分支、依赖、能力和证据关系确定，不由画布坐标确定。为允许跨学科联系，可提供少量相关“跨分支发现”，记录其来源与为何推荐；不能把所有资料默认注入所有成员。

规划是一种可替换的研究贡献。负责提出计划的 Agent 失效后，已成立的任务仍可被认领；宿主承担生命周期、工具授权和原子记账，不承担唯一科研判断。共享宿主故障仍是本地可用性边界，不能宣传完全无中心基础设施。

### 6.2 工作提议的自动与人工边界

在已批准研究目标、数据、工具、计算类型及派生配额内，阅读、问题细化、已允许的候选代码生成和低风险验证可自动继续。以下变化需负责人决定：新研究目标、数据外发范围、新账户／提供方、新依赖信任域、超出资源 envelope、危险操作或无法凭现有证据裁定的重大专业分歧。

提出实验标准是允许的研究活动；使标准成为可信可执行规则是另外的权限。R1 支持从负责人已批准的评价模板中实例化数据、域和容差；新自定义评价器必须独立复核后才可使用，不能由受测候选控制。

### 6.3 共同记忆的可信度分层

“探索区”允许保存猜测、未验证观点、专家意见和反对意见；“已验证区”保存通过声明方法复核的结果与条件。二者可互相引用，不能互相伪装。论文里的指令、仓库 README 和工具返回都作为资料，不成为系统指令。[O04]

摘要包含变更原因与原始引用；有关键数学公式、实验参数或争议时，优先保留原文片段并可展开复核。来源失效或解析不完整时降级置信标记，不补造。跨项目经验初版只允许用户明确选入；不得无差别读取其他私人项目。

## 7. 贡献、路线偏好与资源投入

### 7.1 不使用一个“总成功分”解释全部研究

**成员可靠性**反映遵循契约、有效执行和诚实报告的记录；**贡献价值**反映澄清、证伪、验证或复用带来的研究进展；**路线优先级**反映下一步投入是否值得。三者分别保存，来源可查。

| 新证据 | 路线变化 | 贡献变化 |
|---|---|---|
| 独立复核支持一项重要假设 | 可增加适当后续验证／应用机会 | 接受验证贡献，仍注明范围 |
| 可信反例推翻原条件下的主张 | 减少该主张直接落地机会，可派生边界研究 | 接受反例贡献，不惩罚诚实报告者 |
| 重复引用同一篇论文／同一次实验 | 不新增独立支持 | 不重复计奖 |
| 认证错误、沙箱失败、超时 | 调整执行健康信息，不据此否定科学路线 | 不产生科学奖励 |
| 专家表示看好但未给证据 | 有界调整初始关注或触发调查 | 保持意见身份，不记成验证 |
| 便宜任务大量完成 | 不因数量支配全部配额 | 按贡献去重，不按拆分任务数加分 |

### 7.2 R1 建议策略，而非最优性保证

先生成有出处的分量：证据支持、下一步能减少的不确定性、目标相关性、已证实风险、重复投入和估计成本。所谓“预期信息收益”是待验证估计，不标成实测熵或收益。

分量归一化和组合函数必须有版本、有界且可解释；负责人意见影响值有上限，不可覆盖科学反证与授权。现有 v0.1 继续保留；引入 branch 因子的策略应使用新的版本标识和离线回归，不能沿用 v0.1 名称改变语义。实现不强制某个新 bandit 或强化学习框架。

建议默认将后续可分配机会的 **20%** 留给仍合法、具合理依据的探索分支，**80%** 按当前证据与待验证价值分配。该值是本稿建议，不是统计最优值或付费额度；部署前可配置，运行中变更须留痕。休眠、已明确不适用或越权分支不因探索配额获得执行权。

局部路由只产生建议。路线机会份额由共同研究政策记录，实际任务认领与预算预留使用现有原子机制；不新增一个逐任务强制派发者。机会暂时用完只暂停新增工作，不追溯取消已经获准且状态明确的执行。

### 7.3 安全、终止和恢复

资源下降首先减少未来工作，不粗暴杀死不属于本产品的会话。项目达到用户停止条件、无合法工作、达到 envelope 或发生安全故障时暂停／结束并输出阶段摘要。

未知执行效果必须锁住对应请求、任务与尚不能释放的预留，不能用新 run 绕过。默认沿用现有保守停止语义；未来只有在可证明预算、权限和副作用独立时，才允许不相干分支继续。静态资料阅读与事实复核不应被误标成重试科学执行。

## 8. 自主候选代码与隔离验证：R1 必须打通的主路径

### 8.1 两种实验模式并存

**registered_case**：保留 NIST／synthetic 原程序、固定判据和原检查器，用于回归；不修改结果身份。

**generated_candidate**：[拟建] 接受研究过程中生成的新程序和版本化计划。由独立入口显式选择，不接受 Agent 把未知 CaseId 塞入旧接口，也不通过把动态代码伪装为原示例绕过校验。

现有 `CaseId`／`ScientificCriteria` 和 `ValidationPolicy.executor=literal-files-v1` 都有固定限制。因此，R1 必须设计新的计划、验证报告及批准条件，涉及核心时形成后继核心候选。旧 frozen SHA 继续是证据参照，不能要求它在字节不变的情况下已经实现新契约。[R06][R07]

### 8.2 候选从生成到采用

| 步骤 | 必须产生的对象／证据 | 禁止的捷径 |
|---|---|---|
| 1. 生成候选 | 新版本代码、父候选、来源、目标假设、计划草案 | 直接改宿主、评价器或旧成果 |
| 2. 静态与依赖检查 | scope、语法、文件大小、可疑调用、依赖清单、许可证检查结果 | 认为静态扫描通过等于可安全执行 |
| 3. 冻结实验计划 | 程序与数据摘要、环境 digest、参数、评价器及容差、资源、授权引用 | 看完评价结果再调阈值；动态下载未批准依赖 |
| 4. 执行准入 | 有效 task/token、配额与费用策略、隔离能力证明、独立执行 ID | 前端状态、专家意见或候选自报 PASS 放行 |
| 5. 隔离运行 | 命令、stdout/stderr、原始输出、环境及清理状态 | 宿主直接执行候选；共享可写宿主数据 |
| 6. 独立评价 | 宿主可信重算／独立评价沙箱、假设结论与适用条件 | 信任候选打印的分数、修改判据或提供方账单 |
| 7. 复现／质疑 | 不同成员、新运行和新沙箱；必要时参考实现或反证 | 同一结果复制一份就算独立复现 |
| 8. 准入与后续采用 | 条件明确的源成果；新任务本地再验证、子成果、实际使用记录 | 检索、注入、文件存在或 released 代替 adoption |

**首版代码范围：Python 计算脚本与声明式配置。** 可使用批准镜像中的 NumPy／SciPy／PyTorch 等；多语言协议与前后端架构不意味着首版执行任意 Rust、Julia、C++ 项目。Julia/SciML 等研究后端留在后续能力矩阵中，不阻塞 Python 路径。

### 8.3 拟议 DynamicExperimentPlan 最小字段

```yaml
schema_version: generated-experiment/v1  # 拟议契约，不是现有 API
project_id: <existing-project-id>
branch_id: <research-branch-id>
task_id: <existing-task-id>
candidate_asset_id: <existing-asset-id>
candidate_revision: <immutable-revision>
authorization_ref: <approved-envelope-id>
code_manifest: <immutable-files-and-digests>
data_refs: [<approved-data-version>]
environment_ref: <approved-image-digest-and-dependency-lock>
entrypoint_ref: <trusted-python-script-runner>
parameters_ref: <immutable-parameters>
seeds: [<predeclared-seed>]
evaluation_ref: <independently-approved-criterion-version>
resource_request_ref: <bounded-backend-profile>
network_policy_ref: <deny-by-default-policy>
output_schema_ref: <approved-raw-output-schema>
```

候选可提议输入，执行身份、token、预算批准、执行状态和科学判定由宿主绑定。入口使用结构化参数和固定运行器，不接受通用 shell 字符串作为判定器。数据和代码使用已有资产 ID／标准摘要，不发明新的加密证明系统。

### 8.4 评价与审查独立性

候选作者不得同时拥有可信评价规则写权与最终批准权。候选可读公开问题定义，但不能读取隐藏验收数据、宿主凭据或改写原始参考输出。执行沙箱与评价进程使用独立可写空间。

评价包含数值正确性、必要的边界／初值／守恒或稳定性条件、复现误差与适用范围。PINN 的低训练损失本身不是充分证据，须与独立采样点、参考解或预先规定的物理性质核对。没有标准答案时，结论为有条件支持、反驳或未定；不靠多个 LLM 一致说法替代实验。

Agent 自主生成的评价器代码也属于未信任候选。在独立批准前只能辅助诊断；获准的新评价器要有独立测试、版本和隔离执行方案，不能把它 import 到宿主后直接运行。

### 8.5 独立复现与继承的层次

复现方式分为同代码新环境重跑、独立实现核对、分析／性质检查。报告实际采用哪一种，不以“另一个会话”替代方法独立性。R1 至少支持同代码新环境重跑，并在选定数学任务上使用可信独立评价；不强求每项任务都重新推导另一算法。

代码继承必须证明后续任务实际使用源候选，重新检查适用条件并绑定新结果。对相同条件的复用沿用原消费链；对新条件的应用创建新研究主张与评价，不修改旧条件使其勉强匹配。否定结论也可成为可复用知识，但与“采用一段代码”的回执分开。

## 9. 接口、存储与实现切分

### 9.1 三个平面，只有一个执行事实源

**研究平面**：问题、假设、来源、意见、提议、贡献、路线关系。  
**执行平面**：原生会话、任务账本、租约、预算、沙箱、结果、批准和采用。  
**产品平面**：自然语言入口、三个现有页面、可解释时间线、历史回放和人工决定。

执行平面继续是状态权威；研究平面不能靠“路线完成”设置任务完成，产品平面不能靠 HTTP 200 设置实验通过。后台可以有事件广播、进程监督和只读聚合，它们不是科研总控。前端不得直接修改 SQLite。

### 9.2 复用与新增的工具表

| 操作类别 | 复用现有接口 | 建议增补（名称为拟议） |
|---|---|---|
| 上下文与证据 | `project_context`、`search_evidence` | `submit_research_note`：有来源的假设／评审／质疑 |
| 提议工作 | 原 TaskLedger.enqueue 与派生限制 | `propose_research_work`：在宿主准入后创建合法任务 |
| 认领与接续 | `discover_tasks`、`lease_task` | 保留作用域；返回 branch 与上下文引用 |
| 候选与实验 | `research_candidate`、`research_experiment` | 新版本参数契约及 `prepare_candidate_experiment`，不改旧模式语义 |
| 评价与贡献 | `verify_research`、原报告链 | 版本化三轴结果及独立接受贡献入口；Agent 不传最终奖励 |
| 应用与继承 | `approve_candidate`、`inherit_experience`、`apply_candidate` | 扩展新验证种类，复用身份与采用，不新建平行链 |

具体函数、HTTP 路由与文件路径由实现者核对私库后选择。不得把这张建议表当成当前可调用 API。新 schema 必须标版本；旧客户端遇到不支持能力要显式拒绝，不能悄悄降级成固定案例模式。

### 9.3 研究事件最小公共字段

`event_id`（复用既有机制）、`project_id`、`branch_id?`、`task_id?`、`source_ref`、`actor`、`at`、`schema_version`、`provenance`、`event_kind`、`payload`。

生命周期事件继续复用原 request/run/session/token；额外保存 `correlation_ref` 将 UI 请求、MCP、原生会话、实验和采用关联。反馈事件引用原结果而非重写结果。前端订阅可选现有轮询或事件流，不为了视觉连线引入新的可靠消息集群。

### 9.4 新增模块的边界

建议新增研究语义模块承载对象与局部工作提议；实验契约扩展放在现有 `orchestration/experiments` 边界，准入与应用扩展放在原 `local_assets` 边界。产品私库只负责入口、权限配置、映射与 UI，不内嵌第二份 Router、fencing 或采用实现。

非可信代码不得直接成为宿主插件。数据抽取、引用检索与模型调用走明确受控服务边界；检索优先复用已存在的 SQLite／FAISS 能力。Agent 连接优先使用原 CLI/MCP，后续 ACP、OpenCode 或 OpenHands 均作为适配器，不整体替换底座。

## 10. 执行安全、数据和授权

### 10.1 候选代码的最低执行条件

动态候选一律视为不可信。沙箱至少验证：无宿主工作树任意写权、无账户凭据、无 Docker socket／宿主控制接口、无特权运行、文件导出有范围和大小限制、网络默认拒绝、CPU／内存／进程／时间上限有效、只清理本次拥有的资源。隔离档必须记录实际后端及已验证能力；“使用 OpenSandbox”或“有 Docker”不是安全证明。[O01]

论文解析、仓库内容和候选输出也属于不可信输入，不能导致自动配置新工具、访问秘密或修改系统 prompt。需要外网获取论文／依赖时，由受控获取服务在授权域内完成；候选实验默认离线。[O04]

静态安全检查失败时可以生成修订建议，但不得自动关掉检查器；候选使用未批准依赖时可提交依赖请求，不直接全局 pip install。构建批准环境与运行候选是不同权限，依赖缓存也按项目配置隔离。

### 10.2 项目级授权 envelope

授权至少绑定目标、允许动作、允许数据、Agent／提供方、后端、预算模式、调用／实验／并发上限、到期条件、人工介入节点与停止方式。常规动作在 envelope 内自动进行；修改上述范围须重新批准。

**研究范围被批准不等于已经批准任何费用。** 金额未知可选择保守拒绝或由负责人明确接受非硬封顶的有界运行；二者分开，不把 token 限额写成提供方账单硬上限。总预算不能随分支、run、恢复或派生任务重置。

### 10.3 本地与云的边界

本地主机保有权威项目状态与凭据代理；云推理只接收允许的必要上下文。云计算后端仅接受批准的实验输入，返回结果与清理状态，不成为另一个协作宿主。专家自己的机器是独立安装，可导入／导出成果包，不参与同一个实时共享账本。

共享资料默认不外发；用户可按资料／目录／项目授权发送摘要或原文。引用、日志和导出包均检查秘密与个人数据。无用户请求不推送代码、不发布 Hub／EvoMap、不自动发邮件或投稿。

### 10.4 故障处理

已确认启动前拒绝可向用户说明补充哪些条件；未知结果保留 pending／unknown 和原请求身份，禁止自动再次 POST。过期 token 不可提交，不用同名进程全局清理。暂停项目先禁止新增调用，再按已有取消协议处理拥有的在途工作；不能以“取消请求已发出”写清理完成。

## 11. 三个现有页面的产品规格

| 页面 | 必须呈现 | 主要操作 |
|---|---|---|
| 研究空间 | 研究目标、资料、假设／分支、专家意见、成员、授权余额／未知项、下一步和阻塞 | 提交问题／资料、添加意见、查看研究图、暂停／继续已批准范围、决定范围变更 |
| 任务时间线 | 来源→提议→推荐／实际选择→候选版本→实验→复核／反证→后续行动 | 展开理由与原始证据、比较版本、进入需人工决策项；只暴露当前合法动作 |
| 成果与继承 | 支持与否定结论、条件、代码／报告、复现等级、源／子成果及真实使用 | 导出、引用、提出再验证、查看为何降权／撤回；不直接篡改批准结果 |

用户第一眼看到的是研究问题、发现与下一步，而不是 SHA、fencing 或数据库。技术身份可展开查看。核心数值与原始证据可到达，不能只用模型写的漂亮摘要代替。

黏菌、Section 9／Ghost in the Swarm 是视觉语言，不是数据模型。管道粗细可表达明确标注的路线投入或关联强度；与真实执行规模无关的艺术粒子不得计入成员数。提供中文主界面、可保留英文论文术语和无动画可访问模式；键盘操作和两种既有视窗尺寸继续验证。

历史回放、新离线模拟和本轮真实运行必须有持久可见标记。禁止将旧科研回放与新入口操作混剪成一次新版本完整科研。空结果、解析失败、尚未验证、意见冲突、反例成立、预算待批准和清理未知都属于正常应显示状态。

## 12. 开源复用决策

本节根据 2026-10-02 查阅的一手项目文档制定。上游当前能力不等于冻结依赖已具备同样接口；集成前必须固定实际版本并验证。只引入解决明确缺口的依赖，不为列齐技术栈同时安装多个替代框架。

| 项目／协议 | 决策 | 具体复用与边界 |
|---|---|---|
| OpenSandbox | 继续使用现有执行后端，能力不足时独立适配升级 | 复用生命周期、文件／命令、资源与网络控制；当前核心 SDK 固定 1.1.0，不能套用最新 API。动态候选隔离逐项验证 [R12][O01] |
| MCP | 保留正式研究工具协议 | 新研究工具走身份绑定能力边界；资料不成为指令，不允许 token 透传或任意工具注册 [O04] |
| ACP | 接入抽象参考；新增成员按需采用 | 会话、能力协商、恢复、事件映射适合异构客户端。支持某方法须先协商，不替现有 CLI 增加未验证恢复能力 [O02] |
| OpenCode | 优先参考“启动服务／连接已有服务”同一客户端抽象 | 不强制成为 R1 第三品牌；有明确复用需求再做适配，不接管任意终端 [O03] |
| OpenHands SDK | 按需成员适配与工作区／事件设计参考 | Python/REST、工具和本地／云工作区可复用；不把其规划循环替代全局 Swarm，不同时迁入另一套状态系统 [O05] |
| Docling | 文献解析候选，优先本地、可选依赖 | 解析结构化文本、公式和表格的来源；关键公式仍需复核，模型权重许可单独检查。不是全部知识管理框架 [O06] |
| DeepXDE | PINN 实验镜像中的可选科学依赖 | 参考 PINN／PDE、残差采样与边界条件；首个 Python 切片可选它或直接 PyTorch，不强制二者并行封装 [O07] |
| SciML／NeuralPDE.jl | 后续 Julia 计算后端参考 | 多语言实验的标准输入输出与环境隔离；不作为 R1 必须执行的第二计算语言 [O08] |
| SQLite／SQLModel、Pydantic、FAISS、pytest／Hypothesis | 优先复用仓库已声明的基础设施 | 元数据、契约、检索与性质测试。LangGraph 已安装不意味着必须用于整个群体的中心编排 [R12] |
| ORCA、EvoMap | 保留来源和已有适配边界 | ORCA 借鉴原生接入而非现成主入口；EvoMap 可选经验源，不作为所有研究的联网前置条件 |

多语言采用**协议边界**而不是同进程多语言重写：Python 承载研究／执行服务，沿用产品现有前端语言，通过 JSON Schema／现有 API 契约交互；原生 Rust／TypeScript 等 Agent 作为独立进程或服务接入。候选程序运行语言与 Agent 本体语言分开。

许可证以实际锁定组件为准：Docling 文档注明代码 MIT、模型许可另看；DeepXDE 仓库标注 LGPL-2.1；OpenSandbox 为 Apache-2.0。使用、修改、打包和分发分别保留许可与来源要求，不把“开源”理解为无分发义务。[O01][O06][O07]

## 14. 验收：证明研究闭环，而不是强迫实验出现正结果

### 14.1 验收层级

**L0 契约／确定性测试**：schema、权限、依赖、去重、反馈、候选评估、预算与失败状态。  
**L1 集成／安装测试**：真实产品 HTTP/MCP 到可替换执行边界、构建、独立安装、真实页面，但明确 mock 与真实后端。  
**L2 受授权的真实研究切片**：固定新核心／产品组合，经正式入口完成开放研究主路径。  
**L3 效果研究**：同条件比较单体或其他协作架构，研究效率、质量与新思路；不作为 R1 工程完成的必要大型实验。

不得拿 L0/L1 数量替代 L2，也不得把 L2 单次新思路或复现通过写成 L3 的优势结论。

### 14.2 首个真实切片的建议

推荐一个小型、可解析求参考解的计算问题，例如一维 Poisson 方程：`-u''(x)=π²sin(πx)`，`x∈[0,1]`，`u(0)=u(1)=0`，参考 `u(x)=sin(πx)`。这个示例是建议任务，不是已经批准、已经运行或必须固定的研究题。

给群体论文／方法背景与问题定义，不给完整候选程序。允许它产生如软／硬边界处理、采样方式等有依据的分支；实际选什么由研究过程产生。评价使用独立网格、边界误差和参考解检查，容差及可用环境在评价前确定。参考答案用于防止数值假阳性，不要求候选代码等于某份模板。[O07]

该切片验证从资料到新代码、证据反馈及继承的产品能力，不把“解了已知方程”包装成新论文贡献。后续 Swarm 模拟研究或专家题目使用相同动态契约，不为每个学科硬编码一套新三角色流程。

### 14.4 R1 退出条件

在一个固定新版本组合上，AT-01—18 对应的确定性／集成边界通过，并在一次有授权的研究切片中获得：有来源的新分支、新候选代码、隔离运行、独立复核、证据改变后续行动，以及至少一次真实后续使用。允许研究结论是不支持改进；不要求“战胜基线”。

负结果有科学价值，但若候选未能有效执行、隔离未成立或实际继承未完成，应标对应部分未完成，不把科学诚实当成缺少产品路径的豁免。不能为取得 R1 PASS 无限换种子、换案例、重复付费或删除首失败。

建议请一位未参与实现的人回答“研究什么、实际发现什么、谁复核、后续如何使用、证据在哪”；没有观察者就单列未测，不冒充用户测试通过。

### 14.5 “涌现／效率提升”的后续研究指标

可记录跨成员来源导致的假设修改、非预置问题数、有效反证、独立可接受成果、上下文重述次数、取得合格结果的总用量／时间与人工干预。每项需定义单位、来源和重复规则。

只有设计了相同目标、模型能力、工具、数据、预算及评价口径的对照，才可讨论协作因果收益。新颖性应经文献核对与专家评审；Agent 自称“创新”、一次生成更长答案或动画更复杂不能证明涌现。

## 15. 实现顺序、兼容迁移与停止范围

### 15.1 四个交付切片

| 切片 | 交付内容 | 不做什么 |
|---|---|---|
| M1 共同研究层 | 资料定位、假设／分支／评审、局部上下文、提议到原账本 | 不新增计算后端，不换原生 Agent，不重建任务系统 |
| M2 动态候选安全路径 | 新计划／验证契约、Python 候选、批准环境、隔离及独立评价 | 不放宽旧固定示例；不支持任意语言或宿主执行 |
| M3 证据驱动的下一步 | 三轴结果、反例贡献、去重修订、路线机会与局部策略版本 | 不引入完整强化学习训练平台，不做无人治理自修改 |
| M4 产品纵向闭环 | 三页集成、正式新科研切片、结果导出、独立安装与回归 | 不加大型功能菜单，不额外扩学科／成员品牌，不自动发布 |

M1 的资料输入与 M2 的隔离契约可并行，但动态执行不能在 M2 边界未通过时启用；M3 必须依赖可信评价事件，不从未经复核的 LLM 文本取奖励。每片固定可审查候选，最终运行只使用一个明确组合，不由多条开发分支临时拼接。

### 15.2 不破坏旧承诺

核心 `7062a63` 和产品 `a25aa40` 保留为旧阶段固定证据。R1 新增能力通过新核心／产品版本发布，若新增策略则独立标识，旧 `v0.1` 不变。新增 schema 有迁移与拒绝策略，旧档案只读复核保留其 subject；新生成器不能取得旧科研执行身份。

源码变更后测试与安装应绑定最终候选；docs-only 报告不强制重跑收费科研。旧两类案例主要承担确定性兼容回归，不要求每个 UI 变更重复旧六沙箱实跑。

### 15.3 明确停止扩展

R1 退出条件达到即进入使用反馈。多用户小组、跨宿主 Swarm、更多原生 Agent、Julia／C++ 执行、长期 GPU 调度、自动论文投稿、完整 RSI、计费平台和大规模效果研究全部独立立项。

原始 G0—G1 NIST 产品验收可以独立完成，但不能以它的成功替代 R1 的新候选代码与研究分支能力；也不能把 R1 的新要求反写成旧阶段一直未完成。

## 16. 风险、待确认实现项与开发交接

### 16.1 主要风险及处理

| 风险 | 处理 |
|---|---|
| 固定检查器被误当通用科研判定 | 新动态模式显式版本化；旧检查器只证明旧范围 |
| 新代码、依赖或论文提示注入 | 独立信任边界，候选与评价器隔离，网络和秘密代理分开 |
| 奖励被任务拆分、同源重复或正向偏见利用 | 贡献来源去重，支持／反证分开，独立接受，限额与重复检测 |
| 多 Agent 意见一致但共享同一错误 | 追踪共同来源，要求独立计算／参考，保留争议 |
| 上下文膨胀与费用未知 | 局部检索、来源摘要、运行 envelope、显式停止与使用量口径 |
| 研究路线降温误伤有价值的反例工作 | 路线价值与贡献价值分离，降权可解释且可修订 |
| 产品私库实现未直接审查 | 开发前核对真实路由／安装／文件映射，不从本稿猜 API |
| 过早扩平台与依赖 | 一个计算语言、两个已有原生工具、一个主后端；其余按需适配 |

### 16.2 不重新询问已确认需求，只保留部署前事项

以下不改变 D01—D10，也不阻止 Spec 评审：具体模型与账户、是否启用某个 GPU／云计算后端、批准镜像与依赖版本、真正的预算金额及模式、首个真实研究题目与领域容差、发布方式和外发资料清单。

用户尚未批准这些值，不能由开发 Agent 因为“Spec 已生成”自动填充。单人本地优先、专家意见非一票定案、可靠反例是贡献、动态候选代码进入首版等已确认事项不再作为 TBD。

### 16.3 交给开发 Agent 的解释原则

先建立“FR → 当前代码 → 新增契约 → 验收 AT”的映射；只实现 R1 的闭环缺口。核对上游已存在的能力后复用，不因为 Spec 出现一个对象就创建一个独立微服务。遇到旧验证与新需求冲突，不删除安全检查；提出版本化替代并保留旧行为。

不得把实现细节不明转成频繁向用户询问已有答案，也不得把不相关优化追加为退出条件。需要负责人决定时，给出确切冲突、影响和最小选项。正常范围内的工程选择由开发者作有依据的决策并记录。

## 附录 A：旧限制与新需求的消解

| 看似矛盾的要求 | 本 Spec 的结论 |
|---|---|
| 核心已冻结，但首版要生成新代码 | 历史冻结不改；新目标需新版本契约，不能“包装一下”假装已支持 |
| 无中心调度，但平台可以启动 Agent | 生命周期管理与科研任务决策分开；成员自主认领，宿主做授权和记账 |
| 保留原生 Agent 能力，但不得宿主执行候选 | 允许原生推理、会话和受控写候选；实验只走隔离执行接口 |
| 专家参与，但意见不能一票定案 | 专家提供方向与依据，科学结论由可追溯验证决定；安全／资源负责人仍有否决权 |
| 研究自由推进，但标准要预注册 | 研究问题可演化；每次正式实验的标准和输入在该次评价前冻结，变更建新版本 |
| 失败路线减投入，但反例获得奖励 | 执行状态、假设结论和贡献分别记录 |
| 未验证观点可以交流，但不能污染事实 | 探索区与已验证区分层，可引用且保留来源与状态 |
| 同机并行，但不允许同时写同一 scope | 分支隔离工作区、共享只读证据，沿用原租约和 fencing |
| 论文最终目标，但阶段产物也算价值 | 用阶段成果衡量进展，不承诺每次研究都发表论文 |
